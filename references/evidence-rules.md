## 1. 角色与证据资格

将文稿内容分为：

- **受访者表达**：可作为用户证据。
- **访谈者表达**：只提供上下文，不单独作为用户证据。
- **研究员笔记**：只作为研究员观察或假设，不作为用户原话。
- **系统或转写说明**：只用于判断资料质量。
- **身份不明内容**：默认不作为正式用户证据。只有连续对话关系足以可靠判断说话人时，才标记为“自动识别，推测为受访者”；此类内容最高只能是低置信度的**弱上下文证据**，不得单独支撑核心洞察、用户痛点或产品结论。若有已明确标记的受访者回答独立印证，可形成保守结论，但必须保留身份不确定限制；不得仅因“看起来像受访者”而提高到中或高置信度。无法可靠判断时，列为资料限制、请求确认或排除。

处理简短回答：

- 对“是”“对”“可能”等回答，必须同时保留对应问题。
- 将对引导性问题的简短同意标记为“弱上下文证据”，不得单独支撑核心洞察。
- 受访者后续补充、否定或修正时，以完整上下文解释，不截取早期简短回答。

## 2. 证据编号与引用

### 冻结证据账本与自动校验

对`.docx`、`.md`或`.txt`文件型访谈，先运行`../scripts/build_evidence_ledger.py`生成账本。每个文件独立从`T001`开始编号；访谈者、受访者、简短回应及不明说话人的实际对话都占一个Turn，同一说话人标记或同一时间戳的连续多行合并为一个Turn。账本记录访谈ID、源文件、完整Turn ID、原始定位、说话人别名与角色、原文及转写标记，生成后在本次任务中冻结。

报告前先形成结构化JSON，再运行`../scripts/validate_analysis_evidence.py <ledger.json> <analysis.json>`。校验必须为零错误：引用必须存在、完整且为三位Turn ID；正式洞察证据只能来自受访者；引文必须匹配对应Turn；支持者与证据所属访谈必须一致；支持人数与覆盖状态可复算；洞察为`INS-`、假设为`HYP-`。自动生成访谈ID使用`INT-001`，原文已有稳定ID也可保留，只要完整引用仍形如`INT-SIM-006-T035`。校验失败时不得报告“分析完成”，必须修复结构化结果并重新校验。

使用以下稳定ID：

- 访谈：`INT-001`
- 对话轮次：`INT-001-T001`
- 洞察：`INS-001`
- 待验证假设：`HYP-001`
- 研究员笔记：`INT-001-NOTE001`
- 系统或转写说明：`INT-001-SYS001`

执行以下规则：

- 保留用户已有的稳定ID；缺失时才生成。
- 从“访谈正文”的第一条实际口头对话开始，按原文顺序为全部对话轮次连续编号。访谈者、受访者、身份未标记发言及其他对话参与者都占用一个Turn；不得只给受访者回答编号。
- 标题、访谈元数据、Markdown说明和纯转写状态说明不占用Turn。研究员笔记与系统说明使用独立的`NOTE`或`SYS`编号，不改变后续对话Turn。
- 编号不因输出排序、是否引用或证据有效性而变化。建立“定位ID—说话人—原文”映射后再提取洞察。
- 引用受访者原话，保持原意、条件词和否定词。
- 可以省略无关语气词，但不得拼接相隔很远的句子伪装成一段原话。
- 需要拼接时，分别引用并列出各自证据ID。
- 默认每项洞察展示1至3条代表性原话，并列出全部支持访谈ID。
- 用户要求完整证据表时，列出所有有效证据。
- 输出前逐条核对：引用文本必须存在于对应Turn；同一Turn不能对应不同原话；同一原话在同一访谈中不得被赋予多个定位ID。发现错配时，重新核对映射并同步修复全部引用。
- 不得以`E01`、`E02`等报告内部临时编号替代标准Turn ID。若为阅读体验提供别名，必须同时给出一一映射，例如`E01｜INT-001-T004`；正式洞察和关键证据均须保留标准Turn ID，以便直接回到原始文稿。
- 每一次列举或组合引用都写完整Turn ID；例如写`INT-001-T004、INT-001-T022`，不得把后者缩写为`T022`、`/T022`或其他相对形式。

编号示例：

```text
访谈者：你最近记录过吗？        → INT-001-T001
受访者：记录过。                → INT-001-T002
访谈者：在哪里记录的？          → INT-001-T003
受访者：我写在手机备忘录里。    → INT-001-T004
```

正式用户证据可以引用`T002`和`T004`；第二条受访者回答不能因“受访者回答序号为2”而错误写成`T002`。

## 3. 结论和证据类型

为每项判断分别标记“结论类型”和“证据类型”。

### 结论类型

- **明确事实**：受访者直接描述的行为、经历、偏好、困难或当前做法。
- **合理推断**：由受访者行为和上下文支持，但并非受访者直接说出的解释。
- **待验证假设**：对产品机会、未来行为、付费、价值或原因的进一步判断，需要新访谈或实验。
- **证据不足**：资料无法可靠支持，不进入正式洞察。

### 证据类型

- **直接证据**：原话能够直接支持结论措辞。
- **间接证据**：行为、结果或上下文支持较保守的判断。
- **弱上下文证据**：简短同意、模糊表达或来自引导性提问的回答。
- **无有效证据**：不得用于正式洞察。

一致性规则：

- 明确事实必须具有直接证据或清晰的上下文证据。
- 合理推断必须使用“可能”“显示出”“提示”等保守措辞。
- 待验证假设必须使用 `HYP-` 编号，不得混入已确认洞察。
- 证据不足时写明缺少什么，不为填满字段而推测。

### 行为、意向与当前解决方式

- “以后会使用”“有需要时会使用”“可能继续用”等属于未来使用意向，不得改写为已观察到的使用行为、留存情况、流失状态、使用频率或用户类型。
- 未提供真实使用频率时写“实际使用频率未确认”；不得仅凭意向定义低频、高频、留存、流失或每日使用者。
- “当前解决方式”只记录受访者已经实施的行为、工具或规避动作。未来计划、假设性做法或访谈者建议写为意向、用户方案或未确认；没有证据时写“未提及”或“未确认”。

## 4. 上下文与不确定性

- 保留“可能”“不确定”“不记得”“好像”“如果”等限定词。
- 不将“考虑使用”改写为“愿意使用”。
- 不将“可能付费”改写为“愿意付费”。
- 不将“没找到”直接改写为“功能不存在”。
- 不将用户猜测改写为已验证事实。
- 不将用户提出的功能方案直接等同于底层需求。
- 区分态度和行为，例如“觉得功能不错”不等于“会持续使用”。
- 区分没有提及和明确否定；未提及统一写“未提及”。

### 对象状态与用户感知

- “用户没有看到”不等于“产品没有展示”；“用户不记得反馈”不等于“产品没有反馈”；“用户没有找到”不等于“功能不存在”；“用户不理解页面”不等于“页面设计一定有问题”；“用户认为可能是Bug”不等于“已经确认Bug”。
- 当证据仅反映感知时，使用“受访者当时未能感知到……”“受访者未能确认……”“受访者无法回忆……”等措辞，并说明产品是否存在问题仍需产品证据、可用性测试或行为数据验证。
- 只有文稿或用户提供的产品证据直接验证时，才可陈述产品客观状态；否则不得写“产品缺少……”“系统没有……”“功能存在故障……”或“页面设计导致……”。

引用容易断章取义时，增加前后相邻轮次作为上下文，但仍只将受访者表达标为证据。

## 5. 主题聚合与人数

聚合条件：

- 合并底层问题相同且发生场景相近的表达。
- 场景、后果或目标明显不同的主题保持分开。
- 将用户提出的方案记录在“用户建议”字段，不用方案名称替代痛点名称。
- 不把所有关于同一页面的反馈自动合并为一个主题。

人数规则：

- 以独立受访者为计数单位。
- 同一受访者重复表达一个主题只计1人。
- 同一受访者在不同场景表达不同问题时可支持多个主题。
- 无法确认两段内容是否属于同一人时，不给出精确人数，并说明限制。
- 默认使用“样本覆盖 `n/N_total`”：`n`为去重后的明确支持者数量，`N_total`为本次成功处理的有效独立受访者总数。
- 只有部分受访者覆盖某议题时，另列“议题覆盖基数 `m/N_total`”，并说明在这`m`人中有多少明确支持、条件式支持、反对或不确定。未覆盖者不得被写成“没有需求”。
- 提及人数表示样本覆盖，不表示严重度、价值、优先级或市场规模。

### 支持者核验矩阵

为每个候选聚合洞察先拆出一个可验证的原子结论，再对每位独立受访者标记：

- `S｜明确支持`：原话直接支持完整结论。
- `P｜部分或条件式支持`：只支持结论的一部分，或只在明确条件下成立。
- `C｜相反或纠正`：表达相反观点，或主动纠正了早期表述。
- `M｜混合观点`：同一访谈中同时存在支持与相反表达，不能以单一立场概括。
- `U｜未覆盖或无法判断`：没有谈到该议题、说话人或语义不明、证据不足。

执行规则：

- 每位独立受访者在每项洞察中只能有一个主状态，且`S+P+C+M+U=N_total`。只有`S`直接计入`n`；`P`应促使结论收窄或单列条件式支持；`C`必须进入相反意见；`M`必须单列为混合观点；`U`不得当作支持或反对。
- 使用“全部”“共同”“都”“一致”等词前，确认相关受访者均为`S`。只要存在`P`、`C`或`U`，就改为分层表述或拆分结论。
- 若不同受访者只在抽象上位概念相似，允许使用保守的上位主题，但必须列出具体机制差异，不得写成同一个产品缺陷、原因或解决方案。
- 聚合计数前回看全部单场结果，不只扫描已选代表性证据。若某位受访者符合当前主题定义，应计入；若纳入会使主题失真，应拆分主题。

一致性校验：

- `n = 明确支持者ID去重后的数量`。
- 每位明确支持者至少关联一条有效证据；列出的支持者ID数量与`n`一致。
- 条件式支持者、相反意见者不得混入明确支持者名单。
- 同一受访者重复表达同一主题只计一次；`n`不得大于`N_total`。
- 证据矩阵必须能找到每位支持者的证据；报告中的人数、访谈ID和证据ID相互一致。
- 输出必须分别列出S、P、C、M的访谈ID和U人数；除非另行明确定义，样本覆盖`n/N_total`只计算S。覆盖人数只表示当前样本表达覆盖，不表示重要性、严重度、因果关系、总体比例、市场规模或产品优先级。

示例：若A和B有条件接受提醒，C明确表示已有外部工具且提醒不是缺口，不得写“三人都需要提醒”。应写“样本覆盖2/3为条件式接受，另1/3认为提醒不是当前缺口”，并保留三人的场景差异。

## 6. 矛盾、修正与少数观点

- 同一受访者前后矛盾时，同时保留两种表达及其场景。
- 受访者明确纠正早期表达时，将后续说明作为当前立场，并保留修正记录。
- 不同受访者观点相反时，分别列出支持人数和证据。
- 不用多数观点覆盖少数观点；少数观点可能代表特殊场景或风险。
- 区分真正矛盾与条件差异，例如“重要事项要提醒”和“日常事项别提醒”可以同时成立。
- 无法判断是否矛盾时，列为信息缺口，不擅自解释。

## 7. 隐私遮挡

在输出中的原话和摘要里遮挡：

- 真实姓名
- 电话号码
- 邮箱
- 微信号、账号或用户ID
- 身份证件号码
- 精确住址
- 可直接识别个人身份的工作单位或组合信息

使用 `[姓名已隐藏]`、`[电话已隐藏]`、`[账号已隐藏]` 等占位符。保留与研究问题有关的非识别性信息。明确属于虚构测试数据时仍执行相同遮挡，以验证规则。同时遮挡不必要的第三方姓名。年龄、职业、地点和罕见经历的组合可能重新识别个人；仅在研究问题确有必要时保留，否则将年龄泛化为年龄段、职业泛化为行业或就业状态。论文或课题访谈应提醒使用者遵守既有知情同意和研究伦理范围，但不得自行推断授权状态。

不要在输出其他位置重复暴露已经遮挡的信息。

## 8. 禁止推断

没有直接证据时，不得断言：

- 用户愿意付费或可接受具体价格。
- 某功能一定提升转化、留存或收入。
- 某需求应进入路线图或具有最高优先级。
- 访谈样本代表整体市场。
- 用户具有某种人格、心理状态或疾病。
- 用户话语背后存在未表达的“真实动机”。
- 某群体的特征适用于未访谈的人群。
- 已经达到理论饱和。
- 医学或心理诊断、人格判断、机构或专业责任裁决。

可以将这些内容写为待验证假设，但必须说明验证方式和当前缺失证据。

### 研究边界与验证建议

可以输出用户痛点、场景、当前解决方式、用户提出的方案、相反意见、信息缺口、待验证假设、中立的下一轮研究问题，以及可用性测试或行为数据验证方式。

不得自动输出P0/P1/P2、需求优先级、路线图、开发排期、“应立即上线”、确定性功能设计方案、产品核心指标或其他产品决策。发现可能机会时，转换为`HYP-`：写明当前依据、缺失证据、验证方式，以及什么结果会支持或推翻该假设；“下一轮验证建议”不得替代产品经理作最终决定。

## 9. 异常输入

- **缺少访谈目标**：继续分析，标记结果可能较宽泛。
- **缺少用户标签**：继续分析，不进行群体比较。
- **文稿部分缺失**：只分析可确认部分，列出缺失位置和影响。
- **大量转写错误**：停止受影响段落的洞察提取；其他清晰段落可继续。
- **说话人少量不明**：排除关键身份不明证据，标记B级。
- **自动转写未核对**：仅有自动转写不必然降级；存在明显识别错误、断句异常、说话人错位或关键信息不清时标记B级并说明具体依据。
- **说话人普遍不明**：标记C级并请求澄清。
- **多名受访者混在一起**：能可靠区分时拆分；不能区分时停止人数统计和跨用户聚合。
- **只有研究员总结**：可以整理为“研究员观点”，但不生成用户证据报告。
- **只有一场访谈**：输出单场观察，不使用“多数”“高频”“普遍”等表述。
- **长文稿未处理完**：停止全量聚合，列出已完成范围。

## 10. 终检清单

输出前确认：

- [ ] 所有正式洞察均有有效受访者证据。
- [ ] 所有引用均能通过证据ID回到原文。
- [ ] Turn ID按完整对话轮次生成，而不是只按受访者回答编号。
- [ ] 每条原话与对应Turn完全匹配；同一Turn没有对应多段原话。
- [ ] 引用保留否定、条件与不确定措辞。
- [ ] 访谈者、研究员笔记和身份不明内容未被误作用户证据；自动识别内容已标注低置信度且仅作弱上下文线索。
- [ ] 所有推断和假设均已明确标记。
- [ ] 人数按独立受访者计算且未重复。
- [ ] 每项聚合洞察已完成互斥的`S/P/C/M/U`核验，且各状态人数之和等于有效独立受访者总数。
- [ ] `n`、`N_total`、议题覆盖基数、支持者名单与证据矩阵一致。
- [ ] 已回看全部单场结果以避免漏算；无法纳入同一原子结论的场景已拆分。
- [ ] 相反意见、修正和少数观点未被隐藏。
- [ ] 未提及的信息没有被自行补全。
- [ ] 个人敏感信息已经遮挡。
- [ ] 报告没有宣称产品优先级、市场代表性或未经验证的因果关系。
- [ ] 没有把用户感知错误写成产品客观状态，也没有把未来意向写成实际行为、留存或用户类型。
- [ ] 没有把用户方案写成已验证的最佳方案，或输出P0/P1、路线图、产品指标或确定性功能决策；下一轮验证建议与产品决策已分开。
- [ ] 所有正式洞察均使用`INS-`，所有假设均使用`HYP-`，并已通过证据账本自动校验且为零错误。
